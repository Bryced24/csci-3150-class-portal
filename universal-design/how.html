How to build it

Most accessibility problems come from a short list of mistakes. This page shows how to avoid them in your code and how to test for what you miss.

Start with semantic HTML

Use each HTML element for what it means. Landmarks like header, nav, main, and footer let screen reader users jump between parts of a page. Each page needs one h1, and the other headings should go in order.

<header>...</header>
<nav>...</nav>
<main>
  <h1>Page title</h1>
</main>
<footer>...</footer>

Fix the six most common errors

The WebAIM Million report has found the same six errors at the top of its list for seven years. Those six types made up 96% of all the errors WebAIM detected.

Most common errors on the top one million home pages, February 2026
Error Home pages How to fix it
Low contrast text 83.9% Use a contrast ratio of at least 4.5:1 for normal text and 3:1 for large text.
Missing alt text 53.1% Describe informative images in the alt attribute. Use alt="" for decorative images.
Missing form labels 51% Connect each input to a label with matching for and id values.
Empty links 46.3% Give every link text. An icon link needs a text label for screen readers.
Empty buttons 30.6% Give every button text, or an aria-label if it only shows an icon.
Missing document language 13.5% Add a language attribute like lang="en" to the html element.

Keyboard and focus

  • Make a skip link the first link on the page.
  • Keep the tab order the same as the visual order.
  • Never remove focus outlines. Style them with :focus-visible instead.
  • Make sure keyboard users can tab out of every menu and video player.

Forms and tables

Every form field needs a label. Group related fields with fieldset and legend. Error messages should say what went wrong and how to fix it.

Use tables only for data, never for layout. Give each table a caption, and mark header cells with th and scope.

ARIA only when you need it

WAI-ARIA attributes add information that plain HTML does not cover. The first rule of ARIA is to use a native HTML element whenever one exists. A button element already works with a keyboard and a screen reader, while a div with role="button" needs extra code to do the same thing.

This site uses aria-labelledby to name each section and aria-current to mark the current page in the menu.

Mobile first CSS

Write the phone layout first, then add min-width media queries for wider screens. Use rem units so text grows when someone changes their browser's font size. WCAG 2.2 asks for touch targets of at least 24 by 24 CSS pixels.

.cards {
  display: grid;
  gap: 1rem;
}

@media (min-width: 40em) {
  .cards {
    grid-template-columns: repeat(3, 1fr);
  }
}

This is the CSS for the cards on the home page. They stack on phones and appear in one row on wider screens.

Test your site

Automated tools only catch some errors. They cannot tell you if alt text makes sense or if a page is easy to use, so you need to test by hand too.

  • Run the W3C Nu HTML Checker to find code errors.
  • Run WAVE or Silktide to catch issues like low contrast and missing alt text.
  • Check the heading outline for sections without a heading.
  • Tab through every page without a mouse.
  • Listen to each page with VoiceOver or NVDA.
  • Zoom to 200% and try the site on a real phone.
